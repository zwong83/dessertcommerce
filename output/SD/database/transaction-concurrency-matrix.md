# SweetCommerce Transaction and Concurrency Design

Draft 0.1. PostgreSQL READ COMMITTED with explicit locks. External I/O runs outside transactions. For writes crossing aggregates, lock idempotency record, order/event, charge, day rows in date order, then owner cart. A synchronous command locks only the records it owns or explicitly coordinates. All irreversible effect records and due work are committed together.

| TX | Atomic writes and conflict handling |
| --- | --- |
| TX-01 Identity | Customer verification locks the challenge and consumes it once. Admin challenge issuance/verification and controlled reset lock the existing admin account before any challenge row. Require a current enrolled destination and matching credential epoch. A successful RECOVERY or verified reset advances that epoch and revokes prior sessions in the same transaction; all prior sign-in/recovery codes are stale. If an in-flight verify wins first, reset revokes its new session; if reset wins first, the old verification creates none. Provider sends happen outside TX. Admin login never provisions an admin from contact input. |
| TX-02 Cart | Lock cart, enforce expected version, mutate one line. Row generation changes only if a line was removed and later added. Order snapshots keep the generation, allowing guarded subtraction of only remaining matching quantities. |
| TX-03 Catalogue/capacity configuration | Lock product and scoped media before replacing the gallery. Upload is outside TX. Capacity changes require matching edit/token/day revision under the date lock. Any change to affected-order membership, state, promised date/time or units advances the date revision under the same lock. This includes fee/Cash pending intake or rejection without allocation, plus commitments, cancellations and release. Pending intake updates the revision without reserving units. For date changes lock old/new in order. Keep existing promises; reject caps below active/used counts. Weekly policy changes require their own version and affect new commitments. |
| TX-04 Order and allocation | Submit and abandon lock the same review. Submit consumes it once, creating one order protected by the unique review FK. Abandon returns the committed order if one exists or blocks every later submit of that review. Recheck price, terms and cart version; take a consistent catalogue revision and date lock. Fee/Cash waiting does not allocate. Acceptance commits allocation and consumes matching cart line quantities once. Start prep marks production used. Reschedule records merchant-confirmed customer consent and swaps unused date capacity atomically. For remakes, retain previous USED generations and add a new generation under the same day lock, including on the same date. Count every used generation and allow at most one HELD/COMMITTED generation per order/date/product. Failed reallocation leaves the original promise intact. A separately consented extra charge never rewrites the original total. |
| TX-05 Proof and expiry | Validate and persist an opaque object, lock parent then charge and read the database wall clock. Timely registration preserves standard hold/event window during review. Expiry applies only without timely proof; explicit event rejection releases unused window (DEC-020). Late owned evidence is persisted as reconciliation-only with an open case; it never reopens expired commitments or restores capacity. Deduplicate by charge/digest and clean unlinked objects under bounded retention. |
| TX-06 Settlement | Lock parent and charge, then referenced case or receipt/intent. NORMAL verifies the expected balance and advances only an eligible parent. RECONCILIATION records actual funds by unique reference against an open case without reopening or allocating. For an active underpayment case, SUPPLEMENT posts an independently verified top-up once. Net verified receipts below expected keep the case open; exactly expected may accept once if state, capacity and handoff are still eligible; excess or infeasible funds require reconciliation. Reserve pending refund value before manual payout. Uncertain remains reserved; confirmed non-payout voids; confirmed payout posts once. Protect immutable receipts/refunds from runtime update/delete. |
| TX-07 Event | Persist account-scoped submission intent/digest. Same intent replays and changed payload conflicts. Lock event/current revision and schedule. Check quote minimum and positive instalments before window writes. For consented reschedule, atomically validate and swap unused resources, retaining terms and receipts. Settled balance stays paid. Outstanding due must be future and fall on new MYT date minus three days, with exactly 24 hours' grace. Commit new revision and reminder with the swap. Invalid timing or missing consent leaves case and previous commitments intact. Merchant inability before completion records remaining full-refund obligations. Customer-requested cancellation after transfer has no state or refund effect. Release only unused resources and invalidate obsolete work. |
| TX-08 Durable work | Claim bounded ready batch with a short lease using row locks; send after commit. Use deterministic event key and stable provider reference where supported. Commit attempt and next state only for current lease. An ambiguous provider outcome is flagged for operator review if safe deduplication cannot be guaranteed. |

Retry only database serialization/deadlock aborts for idempotent or uncommitted commands, with bounded jitter and request budget. On unknown commit, clients replay the same scoped key. Domain rejects are returned directly. Safe replays read the committed result without running side effects again.

For customer-requested cancellation, TX-04 or TX-07 checks the no-transfer confirmation, current version and state, proof, receipts, and unresolved transfer cases under the same parent/charge lock order as TX-05 and TX-06. A committed cancellation releases unused resources once. Later evidence takes the existing reconciliation path.

DEC-025: TX-06 checks verified shortfall and active allocation, then records one current top-up window, notice and expiry job under the parent/charge lock. Do not replace an active window. TX-05 registers valid top-up proof during that window; distinguish it from original proof by server receipt time on the same charge. After cutoff, TX-06 accepts only against timely proof for the current window, even if the expiry worker has not run. Expiry locks the same rows and rechecks the job's deadline against the current deadline, review and acceptance. When a timely review ends without settlement after the cutoff, resolve expiry in that review transaction unless another timely proof is pending. Lock the capacity day before releasing unused allocations and retain the settlement case and ledger for reconciliation.

DEC-026: TX-05, TX-06 and TX-07 share the event/charge lock for balance proof, receipt and overdue cancellation. Compare the database clock with the current effective cutoff and check the current deadline revision. Require a merchant bank-check attestation, no timely proof still in review, no recorded balance receipt and no unresolved case indicating possible funds before an overdue cancellation can release resources. Audit the attestation and cancellation reason. No worker cancels a booking for nonpayment.

DEC-028: under the event/charge/case lock, sum independently verified movements less posted refunds. Use one open mismatch case per active charge and deduplicate by bank reference. A request before the existing cutoff commits one notice per case, deadline revision and outstanding amount. It does not mutate the payment deadline or top-up timer. A timely supplement can settle after cutoff if still eligible. Without sufficient timely evidence, leave actual funds in manual reconciliation without reopening resources or treating partial receipt as nonpayment. Existing eligibility and expiry guards still apply.
