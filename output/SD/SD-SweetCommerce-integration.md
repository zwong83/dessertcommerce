# SweetCommerce Integration System Design

Revision 0.5 runtime migration design. [Index](SD-SweetCommerce-index.md) · [OpenAPI 0.4.0 candidate](contracts/sweetcommerce-v1.0.4.openapi.json) · [Backend](SD-SweetCommerce-backend.md) · [Frontend](SD-SweetCommerce-frontend.md). The API schema defines field shape. Backend owns state and enforcement. Browser callers show available actions; server checks govern authorization, settlement and allocation.

The approved increment 1 contract is 0.4.0. Increment 2 uses the [0.4.1 review candidate](contracts/sweetcommerce-v1.0.4.1.openapi.json) for DEC-027–029 and retains the standard-order payloads.

## 1. Boundary inventory and flows

| Boundary | Authority and technical flow |
| --- | --- |
| Customer/admin web → API | Same-origin HTTPS at Next.js. A thin relay forwards the versioned JSON and binary requests to the private FastAPI API, preserving cookies, Origin, CSRF, conditional and idempotency headers, status and response headers. FastAPI uses the contract’s application/problem+json media type for structured errors. Server rendering reads the same API using the caller session. [F01](diagrams/SD-F01.puml), [F02](diagrams/SD-F02.puml), [F03](diagrams/SD-F03.puml), [F05](diagrams/SD-F05.puml), [F08](diagrams/SD-F08.puml) |
| Proof storage → Merchant settlement | Upload and read only through owning server. [F04](diagrams/SD-F04.puml), [F06](diagrams/SD-F06.puml) |
| OTP, WhatsApp, SMS or email | Outbound adapters accept allowlisted channel/payload. OTP is synchronous and bounded. Business notices originate from durable committed facts. [F01](diagrams/SD-F01.puml), [F07](diagrams/SD-F07.puml) |
| DuitNow and Lalamove | Merchant verification or external arrangement. No payment webhook or delivery API for v1. [Standard runtime](diagrams/SD-A02.puml) |

## 2. Request, identity and result

Cookie is host-scoped, Secure and HttpOnly. Mutating authenticated operations use CSRF validation and same-origin checks. Session probe bootstraps an authorized UI after verification or a lost verify response; logout revokes and expires cookie. Admin challenge is role-bound to an enrolled contact. Public OTP failures use a generic outcome and Retry-After on 429. Protected object reads by a different customer return a non-disclosing 404. Admin role denials return 403. Recovery uses the verified merchant channel and controlled enrollment.

| Condition | HTTP and public semantics | Caller handling |
| --- | --- | --- |
| Missing/revoked session; role/origin denial | 401 or 403 | Restart allowed sign-in or show denied; no automatic write replay with a new identity |
| Owned resource missing or hidden | 404 NOT_FOUND | Refresh scoped view without revealing existence |
| Invalid fields, binary, size | 422 VALIDATION, 415 UNSUPPORTED_MEDIA or 413 PAYLOAD_TOO_LARGE | Use field-safe hints or choose valid input |
| Review/fee/quote/terms stale, deadline, capacity or invalid transition | 409 stable typed code | Refresh authoritative response and let the user confirm changed intent |
| Same key, different fingerprint | 409 IDEMPOTENCY_CONFLICT | Only a new reviewed intent receives a new key |
| Rate or dependency failure | 429 with Retry-After, or 503 | Respect budget. Retry writes only with the same key and frozen intent |

Return bounded Problem fields and opaque request correlation. Never expose SQL, secrets, provider bodies or another account's data. Translate internal domain results at the HTTP boundary; log an unexpected failure once.

## 3. Idempotency, deadlines and concurrency

- Mutations carry an opaque UUID key scoped to authenticated actor, operation and fingerprint including target path and canonical body or proof digest. Check committed replay before version checks. Store the minimal result snapshot and protected command reference in the effect transaction. Proposed replay retention is seven days; irreversible order, quote and money guards outlive receipt cleanup. For checkout reload, retain the opaque review ID and inspect its status. If OPEN, use abandon-or-resolve before allowing a replacement submit. It locks the same review as submit and either returns its committed order or makes any late submission impossible. For other commands use the same key or actor-scoped outcome.
- Return monotonic versions; encode If-Match as a quoted decimal. Domain transitions, modified charges and cart edits advance applicable versions. A merchant order action must be legal in its current state even with a matching version. Cash receipt and actual pickup are atomic. Refund intent reserves funds before manual payout and is resolved or escalated after ambiguous outcomes.
- Checkout review binds cart, items, server price and terms, fulfilment/time and expiry. It never holds stock. Recheck at submit, Cash acceptance and merchant fee consent. After review, a changed price/terms or expired offer requires reconfirmation. Final fee offer binds exact version, time and amount before the 30-minute payment window.
- MYT dates govern business rules. Proposed precise boundaries for design: same-day submit through 18:00 and handoff through 21:00; after 22:00 the event lead calculation advances a day. Admin sets explicit MYT deposit/balance due instants within approved day limits; grace adds 24 hours. Deposit odd-sen split rounds up to the nearest sen and balance is the remainder. Extra invoice due 48 hours after recorded actual event end.
- For timed proof, validated registration strictly before deadline under parent/charge lock uses the database wall clock. Timely standard proof preserves the hold. Timely event deposit proof preserves the window under DEC-020. Late evidence remains uploadable against an owned expired or cancelled charge as reconciliation-only, generating a merchant work item without reopening or allocating. Verify independently. Record late or mismatched actual funds against the case without changing commitment, then resolve or use guarded refund. Explicit event rejection releases the unused window.
- Customer cancellation requires `noTransferSent: true` and the current resource version. Under the parent/charge lock, recorded evidence, a verified receipt or an unresolved transfer case blocks customer cancellation with `INVALID_TRANSITION`. This also applies to merchant event cancellation on the basis of a customer request. A post-transfer standard order goes to the configured WhatsApp contact. The app cannot independently observe a bank transfer before it receives evidence.
- DEC-025: for an active verified underpayment, `REQUEST_SUPPLEMENT` commits the customer-visible request, notice work and a deadline 30 minutes after server-issued notice time. `Charge.topUp` exposes the amount, absolute deadline and whether proof is in review. Register valid evidence strictly before that deadline to retain the hold. `SUPPLEMENT` posts one independently verified top-up against the open mismatch case. The net verified total must equal the agreed amount and the order must still be feasible before acceptance. When verifying after cutoff, require timely proof for the current top-up even if the expiry worker has not run. If review ends without settlement past cutoff or expiry finds no timely pending proof, release unused capacity once and route funds to reconciliation. Retrying the request or notice does not restart the window.
- An uncertain refund remains reserved and visible in charge review. Confirmed non-payout voids it and releases the reservation. Confirmed payout references the same intent and posts once. Never initiate a second payout from a new intent after a lost response.
- Merchant records customer consent reference, channel and time for a revised handoff or additional delivery charge. Distinguish promised from actual handoff; failed capacity reallocation preserves the previous promise. A consented charge is separate and groups under standard receipts for reporting. Keep the original accepted total intact.
- DEC-021: if timely deposit proof is verified past the original balance due date, require an explicit merchant disposition and reason. Server rechecks time under lock; if the deadline passed since review and no disposition was supplied, return 409 DEPOSIT_DISPOSITION_REQUIRED. FEASIBLE_24H sets the replacement deadline to 24 hours after verification, without adding another grace period. RESCHEDULE_OR_REFUND records a merchant case without proceeding. Never issue stale reminders or cancel before the applicable deadline.
- DEC-026: for `EVENT_BALANCE`, classify proof against the current `effectiveBalanceGraceEndsAt`, or `effectiveBalanceDueAt` when there is no separate grace period. Preserve the slot while valid timely proof remains in review. `BALANCE_OVERDUE` requires `noBalanceFundsReceived: true` and a reason based on the merchant's bank check, plus a fresh server check of the current cutoff, proof, ledger and unresolved funds under lock. Reject a premature, pending, paid or disputed cancellation with 409 `INVALID_TRANSITION`. A rejected proof alone never confirms nonpayment.
- DEC-027: `rescheduleEventBooking` checks the consented `AGREED_OUTSTANDING` due instant falls on new local event date minus three calendar days and is strictly after the database time. Grace is exactly 24 hours after due. A stale version or invalid plan leaves the case and resource windows unchanged. Only a committed reschedule invalidates old deadline work. `SETTLED` keeps paid state and creates no collection deadline.
- DEC-028: on `EVENT_DEPOSIT` and `EVENT_BALANCE`, `REQUEST_SUPPLEMENT` requires a current verified shortfall and unelapsed applicable cutoff. Commit the request and deduplicated notice with the amount still owed and that cutoff. `SUPPLEMENT` verifies a separate movement in the same open case and reaches acceptance only with exact net verified total and current eligibility. A timely supplement can be reviewed after cutoff. An unresolved shortfall after cutoff is a manual reconciliation case without automatic acceptance, slot change or a new deadline. Preserve the existing proof/expiry rules and distinguish a remaining shortfall from verified nonpayment. Event views use existing `outstandingMinor`, review status, and deadline fields. The `topUp` timer is standard-only.
- DEC-029: reject quote totals of 0 or 1 sen with validation before any quote/window replacement. Two sen splits 1 + 1, and three sen splits 2 + 1. Quote response and storage require strictly positive deposit and balance.

## 4. Bounded queries and channel behavior

Cursor pages default to 25 and cap at 100. Encode filter/order and tuple anchor into opaque cursor; use created/time plus UUID stable tie-breaker and reject cursor/filter mismatch. Merchant calendar is bounded to 31 inclusive local days; financial reporting to 92. Payload budgets include 100 lines per order and 5 MiB for proof. Proposed request time budget: ordinary 5 s; bounded proof transfer 30 s, subject to the business cutoff. HTTP cancellation cancels obsolete reads and cannot undo committed writes.

Adapters send only approved contact and template data. Provider calls use a five-second deadline; one send plus up to three safe retries near 1, 5 and 15 minutes with jitter. Unknown outcomes require provider dedupe/status or manual review before switching channels or replay. OTP failures issue no session. Notices do not alter business state. Read dependency health separately from app liveness.

## 5. Compatibility and contract evidence

Greenfield initial contract. Use additive changes with tolerant readers where possible; version breaking changes, job payloads and fixtures. Do not promote a mixed rollout unless supported versions agree on expected guards and side effects. Provide consumer/provider schema checks, typed problem fixtures, negative role and owner cases, exact deadline/race cases, quote supersession and no per-row queue joins. Trace safe correlation through browser request and work event.

The existing OpenSpec change was prepared against [0.2.0](contracts/sweetcommerce-v1.openapi.json); [0.3.0](contracts/sweetcommerce-v1.0.3.openapi.json) is the previous review candidate. The 0.4.0 candidate changes checkout review/response, merchant action payloads and event schedule/read contracts. Reconcile consumers, fixtures and affected OpenSpec scenarios after review and before Apply. SD 0.5 adds a runtime cutover check for existing sessions, command receipts, checkout reviews, stored media and durable work against the 0.4.0 contract. Production providers, verified templates and fallback remain launch conditions.

Candidate contract verification: reject foreign or retired photo references and stale gallery versions; preserve the saved gallery on invalid media. Verify merchant preview and listed-photo customer rendering for each actual image media type. Race calendar confirmation against an allocated commitment or new pending Cash/fee order. Race admin verification against reset and verify no old code creates a surviving session. Reconcile reports across a MYT date boundary.
